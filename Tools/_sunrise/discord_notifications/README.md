# Уведомления GitHub → Discord

Система заменяет оформитель стандартного GitHub-вебхука. Показывает события разработки, отличает принятие PR от закрытия без слияния, окрашивает одобрения и запросы исправлений, отфильтровывает служебные аккаунты. Публикации списков изменений для игроков остаются отдельными.

## Оформление MoMMI

Визуальный образец — [модуль GitHub из MoMMI, ветка v2](https://github.com/PJB3005/MoMMI/blob/1a10f345dbb709dcae46e6495e522d4d7d6dfbbf/MoMMI/Modules/github.py), коммит `1a10f345dbb709dcae46e6495e522d4d7d6dfbbf`. Оформление реализовано в нашем отправителе без установки MoMMI и его зависимостей.

Карточки PR и задач повторяют расположение элементов образца: автор действия с аватаркой и ссылкой сверху, значок состояния и исходный заголовок, описание с сохранением разметки, голоса за/против, поле `Checks` и предупреждение `status: 🚨CONFLICTS🚨`. Внизу — `репозиторий#номер by автор` и аватар автора. Прежние отдельные поля «Кто выполнил действие», «Автор», строка ветки и словесный статус в заголовке удалены.

Палитра MoMMI: открытые PR и задачи — `#6CC644`, закрытые — `#FF4444`, принятые PR — `#6E5494`. Обычные комментарии и отправки коммитов не имеют цветной полоски. Принудительная перезапись истории выделяется `#FF0000` и подписью `[FORCE PUSHED]`.

Коммиты оформляются как в MoMMI: `**число** New Commit(s) to **refs/heads/ветка**`, затем ссылки на короткие идентификаторы и тексты длиной до 67 символов. По умолчанию выводится до 11 строк; при достижении предела появляется `<.....>`. Описания PR и комментариев обрезаются после 500 символов с окончанием `...`. Подписи `New Comment`, `Created`, `Answered`, `Unanswered`, `Checks` оставлены как в образце; журналы задач по-прежнему русские.

Идентификаторы пользовательских эмодзи взяты из MoMMI и на момент проверки доступны в Discord. Их доступность зависит от владельца исходных эмодзи: если он удалит значок, замените его в TOML. Имя отправителя и изображение `Files/MoMMIv2.png` также задаются настройками, а не скрыты в Python.

MoMMI не содержит образцов для событий рассмотрения PR и ряда других поддерживаемых нами категорий. Они не удалены: используют ту же структуру карточки; одобрения остаются зелёными, запросы исправлений — красными. Новые данные реакций, проверок и конфликтов запрашиваются только на чтение. Их временная недоступность отражается в журнале и не отменяет доставку основной карточки. Состояние самого события не подменяется более поздним состоянием PR.

Ограничения размеров Discord и запрет оповещений через упоминания сохранены. Слишком длинное поле проверок сокращается с маркером `<.....>`, вместо отказа всей отправки. Уже сохранённые карточки в очереди не переоформляются задним числом.

## Как это работает

`Discord Event Capture` сохраняет данные события в файл запуска GitHub Actions. Он не получает секрет Discord и не скачивает игровой код. `Discord Notification Delivery` автоматически забирает этот файл, применяет настройки и отправляет карточку. Поэтому результаты рассмотрения внешних PR тоже проходят через отправитель, не раскрывая секреты их авторам.

Перед отправкой карточка записывается в отдельную служебную ветку `discord-notification-state`. У каждого получателя свой результат доставки. После успешной отправки результат сохраняется; остальные получатели продолжают обрабатываться независимо. Служебная ветка не содержит код игры, ключи доступа или адреса вебхуков. Не объединяйте её с `master` и не удаляйте при обычном обслуживании веток.

Обратите внимание: эта ветка содержит выдержки текста событий. В закрытом проекте не переносите её в публичный репозиторий.

## Первое подключение

1. Включите оба новых сценария в основной ветке своего репозитория. Они лежат в `.github/workflows/sunrise-discord-events.yml` и `.github/workflows/sunrise-discord-delivery.yml`.
2. В GitHub откройте **Settings → Secrets and variables → Actions → Secrets**. Создайте секрет `DISCORD_EVENTS_WEBHOOK` с адресом нужного Discord-вебхука. Для второго канала создайте `DISCORD_EVENTS_WEBHOOK_SECONDARY`. В публичные файлы адреса не вставляйте. Старое окончание `/github` допустимо: отправитель удалит его сам.
3. Во вкладке **Variables** создайте переменную `DISCORD_NOTIFICATIONS_ENABLED` со значением `true`. Без неё новые задачи не выполняют работу. В каждом наследующем репозитории включение и секреты задаются отдельно.
4. Проверьте `config.toml`: события, исключения ботов, цвета, получатели. По умолчанию первый получатель обязателен, второй используется только при наличии секрета. Второй не получает события создания форка — как во второй исследованной подписке Sunrise.
5. Выполните **Actions → Discord Notification Delivery → Run workflow**. Нужны разрешения записи содержимого для служебной ветки и управления Actions для повторного сбора повреждённых/неудачных запусков. Защищённая основная ветка не изменяется.
6. Проверьте сообщения в тестовом канале. Только после проверки отключите заменённые подписки старых вебхуков, иначе часть уведомлений будет дублироваться. Не отключайте отдельные публикации обновлений для игроков.

Для первого запуска берётся история сохранённых событий за `bootstrap_hours`, по умолчанию 24 часа. Старые события, которые новый сборщик никогда не сохранял, автоматически не восстанавливаются.

## Что менять в конфигурации

Файл `config.toml` читается из доверенной основной ветки при каждом запуске отправителя. Для изменения оформления Python редактировать не требуется.

| Раздел | Что настраивается |
| --- | --- |
| `styles.merged` | Фиолетовая карточка принятого PR: `color`, `emoji`, `label`. |
| `styles.approved` | Зелёное одобрение изменений. |
| `styles.changes_requested` | Красный запрос исправлений. |
| Остальные разделы `styles` | Открытие, закрытие, комментарии, редактирование, метки, проверки и другие состояния. Для нового состояния можно добавить раздел с теми же тремя полями; неизвестное использует `styles.default`. |
| `display` | Имя и аватар отправителя, подпись проекта, длина описания, число и длина коммитов; включение проверок и реакций. Пустая подпись проекта означает текущее имя репозитория. |
| `mommi` | Подписи образца, значки голосов и обсуждений, обозначения сокращённого текста и конфликтов. |
| `checks` | Эмодзи состояний проверок: ожидание, выполнение, успех, ошибка и другие исходы. |
| `events` | `['*']` разрешает все действия категории, пустой список выключает её. Например, у `issue_comment` можно оставить только `['created']`, чтобы не показывать редактирования. В TOML допустимы и одинарные, и двойные кавычки. |
| `filters.ignore_bots` | Игнорирование аккаунтов, которые GitHub обозначает типом `Bot`. |
| `filters.ignored_users` | Дополнительные имена служебных аккаунтов, например `Sunrise-Bot` и `PJBot`, которые GitHub считает обычными пользователями. Сравнение без учёта регистра. |
| `filters.branches` | Разрешённые ветки; пустой список означает все. Поддерживаются шаблоны вроде `release/*`. Для PR проверяется ветка назначения. |
| `filters.ignored_labels` | Метки, при которых уведомление не отправляется. |
| `destinations` | Имена получателей, обязательность секрета и исключённые категории. Для дополнительного секрета помимо двух готовых нужно явно передать его через `env` сценария доставки. |
| `delivery` | Число попыток, время ожидания сети, общий предел времени задачи, число отправок за запуск и интервалы повторов между запусками. |

Одобрение человеческого PR ботом и бот-комментарий — разные действия. Слияние человеческого PR служебным аккаунтом сохраняется; остальные служебные события управляются фильтрами. В смешанном `push` служебные коммиты исключаются по отдельности. Упоминания пользователей и ролей в новой ленте не вызывают оповещений.

Пустая строка `color = ""` отключает цветную полоску. `emoji = ""` убирает соответствующий значок. Для чтения дополнительных данных PR сценарий доставки имеет права `checks: read`, `issues: read` и `pull-requests: read`.

Изменение TOML не добавляет новые типы триггеров GitHub Actions: совершенно новую входящую категорию нужно также прописать в YAML. Уже поставленные в очередь карточки сохраняют своё оформление и список получателей — изменение правил не удаляет накопившиеся сообщения.

## Какие события поддерживаются

Автоматически сохраняются открытия и изменения PR, слияния, закрытия без слияния, запросы рассмотрения, одобрения и запросы исправлений, комментарии к PR и к строкам кода, задачи, обсуждения, создание форка, звёзды, отправки коммитов, создание/удаление веток и тегов, выпуски, открытие репозитория и завершённые внешние проверки.

Все ранее использованные категории, документированно отображаемые стандартным Discord-обработчиком, сохранены. `push` и ряд дополнительных категорий теперь также доступны; в исследованных активных вебхуках Sunrise `push` был выключен. Если новые сообщения о коммитах не нужны, задайте `push = []` в разделе `events`.

Для комментариев непосредственно к коммитам (`commit_comment`) у Actions нет триггера. Поэтому отправитель самостоятельно проверяет их через GitHub API при периодическом и ручном запуске. Обнаруживаются новые комментарии и изменения известных комментариев. Короткоживущее событие, созданное и удалённое между проверками, восстановить невозможно.

`star` с удалением звезды, `sub_issues` и `pull_request_review_thread` не имеют прямых триггеров Actions и не входят в документированный список поддерживаемых событий стандартного Discord-обработчика. Они не подменяются выдуманными триггерами. Для точного архива каждого такого события нужен внешний приёмник вебхуков, а не только Actions. Также GitHub не запускает некоторые события, созданные другим сценарием через `GITHUB_TOKEN`; это ограничение источника, не ошибка отправки. [События Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [возможности стандартного обработчика Discord](https://docs.discord.com/developers/resources/webhook#execute-github-compatible-webhook).

## Что происходит при ошибках

| Ситуация | Поведение |
| --- | --- |
| Discord отвечает `429` | Повтор после времени, указанного Discord в `retry_after` или `Retry-After`. |
| Сетевая ошибка, превышено время ответа, ответ `5xx` | Несколько попыток с увеличивающейся паузой. |
| Неверный адрес/ключ, удалённый канал, запрещённая отправка, неправильный размер | Понятная ошибка без вывода секрета. Бессмысленные немедленные повторы не выполняются, карточка остаётся в очереди. |
| Попытки закончились | Следующий запуск повторит доставку. Паузы между запусками растут от `retry_interval` до `max_retry_interval`, чтобы неисправный получатель не мешал остальной очереди. |
| Один канал уже получил сообщение, другой нет | Успешный получатель повторно не обрабатывается. |
| Сборщик завершился с ошибкой | Отправитель пытается перезапустить сборщик, максимум до третьей попытки. Неполученное событие не отмечается обработанным. |
| Заканчивается время задачи | Остаток очереди сохраняется. Работа продолжается новым запуском. |
| Запись состояния в GitHub не подтверждена | Работа останавливается: нельзя продолжать отправку, делая вид, что результаты надёжно записаны. |

Отправитель запускается после сборщика, дополнительно примерно раз в пять минут и вручную. Планировщик GitHub может задерживать запуски; это не обещание доставки ровно за пять минут. Одновременно очередь обслуживает одна задача. Встроенная очередь Actions вмещает до 100 ожидающих запусков; пропуск лишнего сигнала компенсируется следующим просмотром сохранённых событий.

Для восстановления после исправления секрета откройте **Discord Notification Delivery → Run workflow**: ручной запуск не ждёт отложенного интервала повторов. Проверьте итог и количество оставшихся сообщений. Не удаляйте служебную ветку, чтобы «сбросить ошибку»: вместе с ней удалится очередь.

Файлы исходных событий хранятся в Actions до 90 дней либо меньше, если так настроена политика репозитория. Уже принятые в постоянную очередь сообщения не зависят от срока жизни этих файлов. Если сборщик не смог сохранить исходное событие или файлы удалены до обработки, абсолютное восстановление невозможно. Длительно простаивающие публичные репозитории также могут требовать повторного включения расписания GitHub.

Редкий дубль возможен, если Discord сохранил сообщение, но ответ потерялся, либо процесс остановился до записи подтверждения в GitHub. У Discord-вебхуков нет ключа для гарантированного устранения такого дубля. Система предпочитает повторить потенциально недоставленное сообщение, а не молча потерять его.

## Как читать журнал

В сводке запуска отображаются русские пункты: «Сохранено в очередь», «Пропущено» с причиной, «Попытка не удалась», «Успешно отправлено», получатель, заголовок и содержимое карточки, ссылка на GitHub и идентификатор сообщения. Итог показывает количество успешных отправок, ошибок и оставшихся карточек.

Успех сборщика означает только сохранение файла события. Подтверждение Discord находится в запуске отправителя. Зелёный периодический запуск с нулём отправок может означать, что очередь пуста или ещё не наступило назначенное время повтора; это явно записывается в журнал.

## Повторное использование Python

`transport.send_message` принимает обычный словарь сообщения Discord, адрес из секрета и при необходимости список вложений. Поддерживает JSON, multipart-вложения, Components V2 и явные разрешённые упоминания ролей. Функция возвращает ответ Discord с идентификатором сообщения и принимает функцию `report` для записи понятных статусов.

Этот же транспорт уже используется в `Tools/_sunrise/changelog/actions_changelogs_since_last_run.py` и `Tools/_sunrise/discord_publish_announce.py`. Разбор списков изменений, обработка медиа и объявление версии сборки не заменялись новым оформителем событий. Поэтому прежние возможности публикаций остаются на месте, а исправления сетевой доставки общие.

Отдельные модули: `config.py` проверяет настройки, `formatting.py` оформляет данные, `metadata.py` дополняет карточки реакциями и проверками, `github.py` работает с GitHub и состоянием, `deliver.py` управляет сбором и очередью. Не импортируйте пакет через `Tools._sunrise`: существующий родительский пакет содержит посторонние импорты. Задайте `PYTHONPATH=Tools/_sunrise` и используйте имя `discord_notifications`.

## Проверки

Без настоящих отправок, из корня репозитория в PowerShell:

```powershell
$env:PYTHONPATH = 'Tools/_sunrise'
python -m unittest discover -s Tools/_sunrise/discord_notifications -p 'test_*.py'
python -m unittest discover -s Tools/_sunrise/changelog -p test_changelog_actions.py
```

Локальные проверки используют подставные сетевые ответы. Рабочий адрес Discord не должен появляться в тестах, файлах или коммитах. Для реальных проверок создан отдельный закрытый [тестовый репозиторий](https://github.com/ThereDrD0/sunrise-discord-notifier-test-20260909); служебный сценарий создания тестовых PR остаётся только там.

После переноса оформления MoMMI проходят 32 проверки уведомлений и 94 проверки прежней публикации списков изменений. Они проверяют полный состав карточек, расположение элементов, точные цвета, эмодзи, реакции, проверки и сокращение текста. Проверка Python выполняется по правилам Ruff `E,F,I` с пределом строки 79 знаков. Проверочный инструмент установлен временно, зависимостью проекта не является.

[Проверка оформления в настоящем Discord](https://github.com/ThereDrD0/sunrise-discord-notifier-test-20260909/actions/runs/34360407031) успешно отправила семь карточек: открытый, слитый и закрытый PR, одобрение, запрос исправлений, комментарий и коммиты. Проверены поля ответа Discord, включая цвета, заголовки, авторов, подписи и блоки проверок; это не сравнение снимков экрана. [Обычная доставка события GitHub](https://github.com/ThereDrD0/sunrise-discord-notifier-test-20260909/actions/runs/34360007040) отдельно подтвердила оформление закрытого PR и получение настоящей реакции «за».

В настоящем Discord проверены отправки коммитов, одобрение, запрос исправлений, обычный комментарий, слияние PR, закрытие без слияния, задачи и комментарий к коммиту. Первоначальная проверка использовала другую палитру; текущий визуальный контракт проверяется отдельно по значениям MoMMI.

Проверка восстановления: в тестовом репозитории временно установлен неверный ключ. [Запуск с ошибкой](https://github.com/ThereDrD0/sunrise-discord-notifier-test-20260909/actions/runs/34299397583) получил `401` и сохранил четыре карточки. После исправления ключа [ручной запуск восстановления](https://github.com/ThereDrD0/sunrise-discord-notifier-test-20260909/actions/runs/34299571538) завершился успешно, очередь опустела. Ошибки `429`, `5xx` и сети воспроизводились локально, без намеренного превышения лимита настоящего Discord.
