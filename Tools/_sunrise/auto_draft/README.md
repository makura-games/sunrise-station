# Автодрафт

Скрипт `review_threads.js` синхронизирует состояние открытых ПР с ревью GitHub.
Используются последние решения ревьюверов с правом записи в репозиторий, включая
CodeRabbit. Автоматический черновик помечается меткой `auto-draft: unresolved review`.
Ручные черновики без этой метки скрипт не публикует.

## Настройка метки

Имя, цвет и описание задаются в [config.json](config.json), отдельно от JavaScript.
`name` — текст метки, `color` — шестизначный цвет без `#`, `description` — пояснение.
При смене имени добавь прежнее значение в `previousNames`. Бот переименует существующую
метку, сохранив её назначение ПР; старые имена продолжат распознаваться при переходе.
Если меток со старым и новым именем уже две, назначения старой будут перенесены при синхронизации.
Изменения в настройке применяются из доверенной версии сценария, не из ветки автора ПР.

## Результаты и журнал

В проверках каждого ПР есть одна строка «Автодрафт: причина». Её имя меняется вместе
с состоянием, вместо создания нового результата на каждом обходе. Зелёный результат
означает готовность к ревью, а не разрешение на слияние. Нейтральный — ожидание или
ручной режим. Красный — ошибка самой автоматики, а не замечание к коду автора.
Эта информационная проверка не должна назначаться обязательной для самой себя.

В журнале указаны четыре этапа: чтение ревью, чтение проверок, обновление комментария
и применение решения. Итог с причинами также записывается в Summary — сводку запуска.
Сбой одного ПР не мешает проверять остальные. При ограничении запросов GitHub обход
останавливается: готовность непроверенных ПР не подтверждается.

После установки в master ближайший запуск по расписанию проверяет все открытые ПР
с постраничным чтением. Новый коммит для старых ПР не нужен. Ручные черновики и ранее
выданный ручной аварийный переход сохраняются. Первый обход создаст список задач
в каждом ПР — прямые вебхуки Discord с событием `issue_comment` могут переслать их.

Текущая политика:

- Новое `Request changes` переводит готовый ПР в черновик.
- `Approve` заменяет требование исправлений только того же ревьювера.
  Незакрытые обсуждения предыдущих `Request changes` того же автора сохраняют
  блокировку между повторными требованиями. Обсуждения из `Comment` не блокируют ПР.
- Для автоматической готовности нужны успешные обязательные проверки и завершённое
  ревью CodeRabbit последнего коммита, а также отсутствие незакрытых требований.
  Закрытия обсуждений самого по себе недостаточно до завершения проверок.
- `Request changes` без обсуждений остаётся блокирующим до нового решения,
  отмены ревью или ручного перевода ПР в готовое состояние.
- Ручной перевод в готовое состояние остаётся аварийным обходом проверок и старых
  замечаний. Новое требование исправлений после него снова включает автодрафт.
- Если CodeRabbit явно сообщил о лимите, ожидание его ревью
  по умолчанию пропускается. Это не отменяет обязательные проверки и уже открытые
  требования исправлений.
- Если в течение 10 минут после создания ПР нет ни комментария, ни ревью, ни проверки
  CodeRabbit, пункт зачёркивается и перестаёт блокировать открытие. Это отсутствие
  активности, а не достоверное определение установки приложения. Поздний ответ бота
  снова включает его проверку. Ошибка API не считается молчанием.

Обязательные проверки берутся из правил целевой ветки GitHub, включая правила
организации и классическую защиту ветки. Ещё не появившаяся обязательная проверка
считается ожидающей. При перезапуске используется последний результат; одноимённые
задания разных workflow остаются независимыми. Пропущенное или нейтральное задание
считается допустимым по правилам GitHub.
Уже готовый ПР не возвращается в черновик только из-за ожидания повторного запуска
ранее успешных проверок того же коммита. Новый коммит, провал проверки или открытое
требование исправлений по-прежнему блокируют. Сам черновик всегда ждёт окончания
последнего запуска перед автоматическим открытием.
Обязательные сценарии из правила `workflows` проверяются отдельно по пути,
репозиторию-источнику и заданной версии. Пока успешный запуск текущего коммита
не найден, переход из черновика запрещён. Сбой чтения GitHub не меняет состояние ПР.

## Список задач в ПР

Приложение поддерживает один комментарий «Готовим изменения к ревью»: замечания,
CodeRabbit и обязательные проверки с автоматически заполненными галочками.
Все пункты выполнены — автоматический черновик открывается. Для ручного черновика
остаётся отдельный пункт подтверждения готовности автором.

Ручные изменения текста и галочек восстанавливаются по событию редактирования;
удалённый комментарий создаётся заново. Расписание страхует пропущенные события.
Пользовательские копии списка не учитываются. Приложение должно быть выделено
только для автодрафта: его собственные верхнеуровневые комментарии считаются
служебным списком даже после удаления скрытого маркера человеком.

Связанные названия в Actions:

- `PR: Automatic Draft Management` — читает состояние GitHub, обновляет список и черновик.
- `PR: Automatic Draft Management - Review Events` — сообщает первому сценарию об изменении ревью; секретов и права записи у него нет.

## Ограничение запросов CodeRabbit

Переменная Actions `AUTO_DRAFT_ALLOW_CODERABBIT_RATE_LIMIT` управляет послаблением:

- Отсутствует или равна `true`: подтверждённый лимит разрешает пропустить ревью.
- Равна `false`: ПР ждёт завершённого ревью даже при лимите.

Пример отключения после перехода на другой тариф:

```powershell
gh variable set AUTO_DRAFT_ALLOW_CODERABBIT_RATE_LIMIT --repo makura-games/sunrise-station --body false
```

Учитываются уведомления настоящего `coderabbitai[bot]` и его статусы проверки:
короткие ответы `Review rate limited`, сообщения об исчерпанной квоте и полные
служебные блоки. Хеш коммита и конкретная разметка не обязательны. Пользовательская
копия уведомления не засчитывается. Более поздний статус начавшейся проверки
отменяет старое уведомление: бот уже приступил к новому проходу.

CodeRabbit должен проверять черновики (`reviews.auto_review.drafts: true`),
иначе он перестанет автоматически проверять исправления после автодрафта.

## Установка GitHub App

Приложение принадлежит организации `makura-games`. Его нужно установить только на
`sunrise-station`, `project-fire`, `lust-station`, `fish-station`, `invicta`.
Наличие приложения и секретов само по себе не обновляет workflow других репозиториев:
для перехода с прежнего `AUTO_DRAFT_TOKEN` туда также требуется перенести реализацию.

1. Владелец организации открывает [заполненную форму регистрации](https://github.com/organizations/makura-games/settings/apps/new?name=Makura%20Auto%20Draft&url=https%3A%2F%2Fgithub.com%2Fmakura-games%2Fsunrise-station&public=false&webhook_active=false&contents=write&issues=write&pull_requests=write).
2. Проверяет права репозитория: `Contents`, `Issues`, `Pull requests`, `Checks` — чтение и
   запись; `Actions`, `Commit statuses`, `Metadata` — чтение. Права организации и пользователя не нужны.
   Webhook выключен, установка — `Only on this account`.
3. Создаёт приложение, затем `Install App` → `makura-games` → `Only select repositories`
   и отмечает пять репозиториев выше.
4. Копирует `Client ID`, затем в `Private keys` нажимает `Generate a private key`.
   Скачанный `.pem` хранится вне репозитория.

Создание приложения требует подтверждения в браузере. `gh` используется для
последующей настройки и проверки через API. Манифест приложения также требует
веб-подтверждения и не устраняет этот шаг.

## Переменная и секрет

Нужны `AUTO_DRAFT_APP_CLIENT_ID` и `AUTO_DRAFT_APP_PRIVATE_KEY`. Можно создать их на
уровне организации с доступом только к пяти репозиториям. Для токена `gh` это требует
области доступа `admin:org`; при необходимости владелец выполняет
`gh auth refresh --hostname github.com --scopes admin:org`.

Если общие секреты недоступны, администратор репозиториев может настроить каждый
репозиторий отдельно, используя имеющийся доступ `repo`:

```powershell
$appClientId = Read-Host 'Client ID приложения'
$appKeyPath = Read-Host 'Полный путь к скачанному .pem'
$appPrivateKey = Get-Content -LiteralPath $appKeyPath -Raw -ErrorAction Stop
$repositories = 'sunrise-station', 'project-fire', 'lust-station', 'fish-station', 'invicta'
foreach ($repository in $repositories) {
    gh variable set AUTO_DRAFT_APP_CLIENT_ID --repo "makura-games/$repository" --body $appClientId
    if ($LASTEXITCODE -ne 0) { throw "Не удалось настроить переменную: $repository" }
    $appPrivateKey | gh secret set AUTO_DRAFT_APP_PRIVATE_KEY --repo "makura-games/$repository"
    if ($LASTEXITCODE -ne 0) { throw "Не удалось настроить секрет: $repository" }
}
```

## Проверка

Локальные проверки без доступа к GitHub и без изменения ПР:

```powershell
python Tools/_sunrise/ci/test_auto_draft_review_threads.py
node --check Tools/_sunrise/auto_draft/review_threads.js
node --check Tools/_sunrise/auto_draft/readiness.js
node --check Tools/_sunrise/auto_draft/checklist.js
```

Ручная проверка установленного приложения на выбранном ПР:

Для ручного запуска файл workflow с `workflow_dispatch` должен уже существовать
в основной ветке. В `sunrise-station` это условие выполнено прежней реализацией.
При первом переносе в другой репозиторий сначала нужно зарегистрировать workflow
в его основной ветке.

```powershell
gh workflow run sunrise-auto-draft-review-threads.yml --repo makura-games/sunrise-station --ref fix/auto-draft -f pr-number=4644
```

При ручном запуске код берётся из коммита выбранного workflow. При автоматических
событиях — из доверенной версии workflow, а не из ветки контрибутора. Пустой
`pr-number` запускает синхронизацию всех открытых ПР и может изменить их статусы.

Проверить успешное создание токена приложения, затем на тестовом ПР проверить
`Request changes` → черновик, `Approve` → готовность к ревью и закрытие обсуждений
→ готовность к ревью. События ревью передаются через отдельный непривилегированный
workflow. Автоматическая цепочка `workflow_run` заработает после попадания файлов
в основную ветку. Закрытие обсуждений проверяется по расписанию примерно раз в пять
минут; GitHub может задержать или пропустить запуск.
Если событие не содержит номер ПР, скрипт ищет открытые ПР по коммиту сигнального
запуска. Полный обход остаётся резервом, если GitHub не вернул связанных ПР.
Завершение сборки и YAML-проверки, изменение статуса коммита и сообщение CodeRabbit
также запускают пересчёт. Расписание подхватывает остальные изменения проверок.
Состояние проверок и публикация отчёта используют токен приложения. Для существующей
установки после добавления прав `Checks`, `Actions` и `Commit statuses` владелец должен
подтвердить новые разрешения установки. До подтверждения новый сценарий не сможет
создать токен с нужными правами. Штатный `GITHUB_TOKEN` не используется: его меньший
лимит не подходит для полного обхода сотни ПР каждые пять минут.

Старый `AUTO_DRAFT_TOKEN` удаляется отдельно в каждом репозитории только после
перехода его workflow на приложение и успешной проверки. Отзыв личного токена
выполняет выпустившая его учётная запись после проверки всех его потребителей.
