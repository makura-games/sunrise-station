# Уведомления GitHub в Discord: варианты замены стандартной интеграции

> Историческое исследование до реализации. Инструкция готового уведомителя: [discord_notifications/README.md](discord_notifications/README.md).

Дата исследования: 9 сентября 2026 года. Это исследование, не реализация: сценарии автоматизации, секреты и настройки GitHub/Discord не изменялись; тестовые сообщения не отправлялись.

Для работы создана локальная ветка `research/github-discord-notifications` от локального `master`, коммит `17e500bbc7f8b7a7db4b2780dbd0f35cffda0385`. На момент проверки удалённый `master` указывает на тот же коммит.

## Короткий вывод

Для Sunrise разумно начать с **GitHub Actions — автоматических задач, которые GitHub запускает при событиях в репозитории**. Постоянно работающий отдельный сервер для этого не нужен.

Есть два практичных пути. Если подходит настройка в YAML и готовое оформление, стоит сначала испытать готовое действие **Pipeline Pling**. Если нужен отдельный TOML-файл, свои русские подписи, комментарии и точные правила для служебных аккаунтов — лучше небольшой собственный уведомитель на уже используемом Python. Не большой Discord-бот и не новая платформа автоматизации.

Централизованный сервис-посредник имеет смысл, если нужно сразу обслуживать всё семейство проектов, собирать подробную ленту комментариев и надёжно переживать большие очереди. Для нескольких важных уведомлений в день это лишнее обслуживание.

Главная находка: проблема не только в оформлении. В доступной истории одного действующего вебхука **73 из 725 попыток доставки получили ответ Discord `429` — превышение частоты запросов**. Поэтому фильтрация и повторная отправка после временных отказов важнее декоративных улучшений.

## Что означают основные слова

**PR, или запрос на слияние**, — предложение включить изменения в проект. Его можно принять, объединив изменения с основной веткой, или закрыть без принятия. Это разные исходы.

**Вебхук** — автоматическая отправка данных на специальный адрес. GitHub сообщает: «произошло событие», а Discord принимает сообщение. В текущей схеме преобразование выполняет встроенный обработчик Discord для GitHub.

**Карточка сообщения** — оформленный блок с цветной полоской, заголовком, кратким описанием и ссылкой. Для публикации таких карточек достаточно обычного вебхука Discord: отдельная учётная запись Discord-бота не обязательна. [Документация Discord](https://docs.discord.com/developers/resources/webhook).

**Форк** — отдельная копия репозитория. Но проект может наследовать код Sunrise и при этом технически не числиться форком на GitHub. Для настройки уведомлений это существенно.

## Что сейчас настроено в репозитории

Проверка выполнена через `gh` — официальную командную программу GitHub. Старый адрес `space-sunrise/sunrise-station` перенаправляется на [makura-games/sunrise-station](https://github.com/makura-games/sunrise-station). Репозиторий публичный, основная ветка — `master`. Адрес удалённого репозитория в локальных настройках не менялся.

На уровне репозитория обнаружены два включённых вебхука Discord с окончанием `/github` и один выключенный вебхук. У двух включённых вебхуков разные адреса; это само по себе не доказывает, что они направлены в разные каналы. Каналы Discord не проверялись, закрытые адреса в отчёт не включены.

Активные вебхуки подписаны на PR, комментарии, результаты рассмотрения PR, задачи и некоторые другие события. **На `push` — отправку коммитов в репозиторий — оба сейчас не подписаны.** Поэтому приведённая ниже оценка коммитов нужна для возможного расширения ленты, а не как описание текущих подписок. Проверить подписки администратор может в [настройках вебхуков репозитория](https://github.com/makura-games/sunrise-station/settings/hooks).

Вебхуки всей организации проверить не удалось: текущей авторизации не хватает права `admin:org_hook`. Это ограничение проверки, а не доказательство их отсутствия. Дополнительные права не запрашивались.

В проекте уже есть отдельная отправка списков изменений для игроков и объявлений об обновлении сервера:

- `.github/workflows/sunrise-publish-discord-changelog.yml` и `.github/workflows/sunrise-dispatch-discord-changelogs.yml` — публикация списков изменений после сборки.
- `Tools/_sunrise/changelog/targets` — отдельные настройки получателей, содержащие имена секретов, а не сами закрытые адреса.
- `Tools/_sunrise/changelog/actions_changelogs_since_last_run.py` — оформление сообщений и обработка ограничения частоты Discord.
- `Tools/_sunrise/discord_publish_announce.py` — объявление об обновлении сервера.

Это полезный местный опыт, но не готовая замена журналу событий разработки. Не стоит смешивать «PR принят» и «изменение уже установлено на игровом сервере»: между ними может пройти время. Исходники доступны в [каталоге автоматизации Sunrise](https://github.com/makura-games/sunrise-station/tree/17e500bbc7f8b7a7db4b2780dbd0f35cffda0385/Tools/_sunrise).

Примеры можно посмотреть непосредственно в [PR #4725](https://github.com/makura-games/sunrise-station/pull/4725), [PR #4732](https://github.com/makura-games/sunrise-station/pull/4732), [PR #4799 с длинным описанием](https://github.com/makura-games/sunrise-station/pull/4799) и [коммите с длинным сообщением](https://github.com/makura-games/sunrise-station/commit/17e500bbc7f8b7a7db4b2780dbd0f35cffda0385).

Отдельно изучена доступная история одного активного вебхука: с **6 сентября 12:32 до 9 сентября 02:43 по Москве**, примерно 62 часа. В ней 725 попыток доставки: 652 ответа `204` и 73 ответа `429`. Среди событий — 214 комментариев к строкам кода, 198 обычных комментариев и 165 событий PR. Только редактирований обычных комментариев — 152.

В проверенных отдельных доставках комментарии и результаты рассмотрения отправлял `coderabbitai[bot]`. В одном из отказов Discord прямо потребовал подождать 0,3 секунды перед повтором. Это подтверждает кратковременные всплески, а не только большой месячный объём. При этом **725 доставок — не 725 видимых сообщений Discord**: часть типов событий встроенный обработчик может не отображать.

GitHub не повторяет неудачные доставки вебхуков автоматически. Поэтому нельзя рассчитывать, что отклонённое сообщение само появится позже. [Обработка неудачных доставок GitHub](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries), [ограничения частоты Discord](https://docs.discord.com/developers/topics/rate-limits).

### Ограничения измерений

Статистика PR получена из полной выборки 169 PR, обновлённых начиная с 9 августа, с последующим отбором нужных дат создания, слияния и закрытия. Описания измерялись в текущем виде, включая разметку и скрытые комментарии шаблона; это не длина видимого пользователю текста. Для подсчёта использована длина строки .NET, поэтому отдельные эмодзи могут занимать больше одной позиции.

Коммиты посчитаны локально по основной линии истории с `git log master --first-parent`. Коммиты в непринятых PR туда не входят. Большой PR не означает столь же большой пакет вебхука: GitHub не вкладывает в каждое уведомление весь изменённый код.

Для публичного Sunrise использование стандартных исполнителей GitHub Actions бесплатно. На закрытые репозитории и более мощные платные исполнители это обещание не распространяется. [Правила оплаты Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

У Cloudflare Workers бесплатный предел — 100 000 запросов в день. У Cloudflare Queues, отдельной службы очередей, есть бесплатные 10 000 операций в день; один запрос GitHub не равен одной операции очереди. Для измеренной нагрузки запас выглядит достаточным, но это оценка, а не проверка развёрнутого сервиса. [Тариф Workers](https://developers.cloudflare.com/workers/platform/pricing/), [тариф Queues](https://developers.cloudflare.com/queues/platform/pricing/).

## Подробнее о готовом действии Pipeline Pling

Проверена версия `v1.5.0`, опубликованная 27 июля 2026 года. Сам репозиторий создан 8 июля 2026 года: наличие нужных функций подтверждено, а многолетней истории эксплуатации пока нет. Просмотрены описание, параметры и исходники; действие не устанавливалось и не запускалось. [Проверенная версия](https://github.com/Qbox-project/pipeline-pling/releases/tag/v1.5.0).

Оно различает слияние и закрытие без слияния, позволяет настраивать цвета, ветки, метки и объём описания. По умолчанию выдержка описания ограничена 320 знаками, обычный список коммитов — десятью. Это уже гораздо ближе к нашим размерам PR, чем пересылка всего текста. [Параметры действия](https://github.com/Qbox-project/pipeline-pling/blob/v1.5.0/action.yml), [оформление коммитов](https://github.com/Qbox-project/pipeline-pling/blob/v1.5.0/src/message.ts).

Два ограничения особенно важны для Sunrise:

1. `skip-bots` проверяет тип отправителя события. У `Sunrise-Bot` и `PJBot` GitHub возвращает тип `User`, поэтому понадобятся дополнительные условия по именам. Кроме того, слияние человеческого PR ботом не обязательно нужно скрывать вместе с бот-комментариями. [Проверка отправителя PR](https://github.com/Qbox-project/pipeline-pling/blob/v1.5.0/src/pull-request.ts).
2. После временного отказа выполняется только один повтор — две попытки всего; ожидание ограничено 30 секундами. Это лучше отсутствия повторов, но не полноценная очередь для продолжительного сбоя или большого потока. [Реализация отправки](https://github.com/Qbox-project/pipeline-pling/blob/v1.5.0/src/discord.ts).

Итог: хороший кандидат на короткую пробу в отдельном канале, но не готовое решение «поставил TOML и получил всю ленту разработки». Если начинают требоваться обёртки для каждого правила и переделка подписей, преимущество готового действия исчезает.

Дополнительно просмотрены готовые посредники. У [futuritywork/github-discord-webhook](https://github.com/futuritywork/github-discord-webhook) заявлены открытия и закрытия PR, но требуются отдельная служба, PostgreSQL и управление пользователями. [freya022/github-discord-webhook-proxy](https://github.com/freya022/github-discord-webhook-proxy) ориентирован на распределение событий по темам форума Discord. По опубликованным возможностям они не выглядят более прямым решением всей нашей задачи; полноценный аудит этих проектов не проводился.

## Как должна выглядеть удобная конфигурация

TOML подходит: это обычный текстовый файл с именованными настройками, списками и разделами. Используемый проектом Python 3.12 уже умеет читать его через стандартный модуль `tomllib`; отдельная библиотека для этого не нужна. YAML тоже разумен: он уже используется в настройках получателей списка изменений. [Документация `tomllib`](https://docs.python.org/3/library/tomllib.html).

Ниже — предлагаемое содержание настроек, а не существующий формат или готовый код:

| Настройка | Для чего нужна | Разумное начальное значение |
| --- | --- | --- |
| Какие события показывать | Не превращать канал в копию всей технической активности | Открытие, повторное открытие, готовность к рассмотрению, слияние и закрытие PR. |
| Какие ветки учитывать | Убирать рабочие и временные ветки из общей ленты | `master`, при необходимости `stable`; для PR проверять ветку назначения. |
| Какие аккаунты игнорировать | Отделить служебную активность от человеческой | Тип `Bot` и явный список `Sunrise-Bot`, `PJBot`; применять с учётом вида события. |
| Что делать с комментариями | Управлять главным источником частых сообщений | Изначально выключены; при необходимости включить только новые человеческие комментарии, без редактирований. |
| Сколько текста показывать | Сохранить читаемость на телефоне | 300–500 знаков описания и ссылка на полный PR. |
| Сколько коммитов перечислять | Не засорять канал при больших обновлениях | 5–10 первых строк и ссылка на полное сравнение. Одно сообщение на `push`, а не на каждый коммит. |
| Как показывать исход PR | Сразу видеть, принято изменение или отклонено | Разные подписи и цвета для слияния и закрытия без слияния. |
| Куда отправлять | Разделять проекты или виды уведомлений | Имя секрета/получателя, но не закрытый адрес в публичном файле. |

Отдельный файл правил не отменяет настроек самого GitHub Actions: перечень событий, запускающих задачу, задаётся в YAML. TOML управляет дальнейшей фильтрацией и оформлением. Для добавления совершенно нового типа входящего события может понадобиться изменить и YAML.

Фильтр ботов не должен означать «скрыть всё, к чему прикоснулся бот». Например, комментарий `coderabbitai[bot]` можно убрать, но принятие человеческого PR автоматическим помощником — оставить. Для смешанной отправки коммитов человеком нужно фильтровать сами коммиты, а не выбрасывать всю отправку из-за одного служебного изменения.

## Какими сделать сообщения

GitHub уже передаёт признак принятого PR. Слияние тоже приходит как закрытие, поэтому смотреть только на `closed` недостаточно: нужен `pull_request.merged`. По этому признаку можно сделать фиолетовую карточку «Изменения приняты» и красную «Закрыто без принятия». [Событие слияния PR](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-pull_request_target-workflow-when-a-pull-request-merges).

Для PR достаточно названия проекта, номера и заголовка, явного результата, автора, человека или службы, выполнивших действие, и короткого описания. Цвет дополняет подпись, а не заменяет её. Для большого обновления — количество коммитов/файлов и ссылка, без полного списка.

В классических карточках Discord заголовок ограничен 256 знаками, описание — 4 096, отдельное значение поля — 1 024, весь текст карточек одного сообщения — 6 000. Обычный текст сообщения ограничен 2 000 знаками. Поэтому сокращать нужно с учётом всех полей, а не только основного описания. [Ограничения карточек](https://docs.discord.com/developers/resources/message#embed-limits), [отправка вебхуком](https://docs.discord.com/developers/resources/webhook#execute-webhook).

Из описаний стоит удалять скрытые комментарии шаблона и не переносить целиком служебные инструкции. Изображения и видео на первом этапе лучше оставить по ссылке на PR: это журнал разработки, а не ещё одна публикация полного списка изменений для игроков.

## Что обязательно учесть при реализации

### Внешние PR и права доступа

Обычный сценарий `pull_request` для PR из чужого репозитория не получает секрет Discord. Для уведомления о жизненном цикле PR подходит `pull_request_target`, работающий в контексте принимающего репозитория. Он должен исполнять только доверенный код и читать правила из основной ветки, **не запускать код или конфигурацию из предложенного PR**. Это особенно важно при 83% внешних PR. [Условия выполнения событий PR](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [правила безопасного использования](https://docs.github.com/en/actions/reference/security/secure-use).

Сейчас общий токен Actions в Sunrise по умолчанию имеет права записи. Новому уведомителю нужны явно ограниченные права: отправка в Discord сама по себе не требует права изменять репозиторий. Заголовки и описания PR нужно воспринимать как данные, а не вставлять в исполняемые команды. Упоминания вроде `@everyone` должны быть запрещены настройкой `allowed_mentions`. Сторонние действия следует закреплять за проверенным коммитом, а не изменяемой веткой.

События, созданные автоматизацией через `GITHUB_TOKEN`, не всегда запускают следующие сценарии. Для `push` это особенно важно. В актуальных правилах есть исключения для ручных/программных запусков и некоторых событий PR с подтверждением; считать Actions точной копией потока вебхуков нельзя. Не нужно выдавать новый мощный токен только ради уведомлений: при необходимости отправку можно явно вызвать из создающей событие задачи. [Актуальные правила запуска](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

### Частота, повторы и большие пакеты

При `429` отправитель должен подождать указанное Discord время `retry_after` или `Retry-After` и повторить запрос. Временные сетевые ошибки и ответы `5xx` тоже требуют ограниченных повторов. После исчерпания попыток должна оставаться видимая ошибка, а не сообщение «всё успешно». Фиксированное правило «столько-то сообщений в секунду» не заменяет обработку ответа сервера. [Правила Discord](https://docs.discord.com/developers/topics/rate-limits).

В Actions теперь есть `concurrency` с `queue: max`: до 100 ожидающих запусков в группе. Это позволяет последовательно отправлять небольшую ленту без отдельной службы очередей. Но простой `cancel-in-progress: false` без `queue: max` сохраняет только один ожидающий запуск; последующие его заменяют. При заполнении очереди новые запуски отменяются. Группа действует в пределах репозитория, поэтому общей очередью для Sunrise, Fish и Fire она не является. [Документация очереди Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

У центрального посредника порядок другой: проверить подлинность запроса GitHub, надёжно принять событие в очередь, быстро подтвердить приём, затем отправлять в Discord с повторами. GitHub ожидает ответ в пределах 10 секунд. Для повторных доставок можно учитывать идентификатор `X-GitHub-Delivery`, чтобы повторная обработка не создавала дубликат. [Рекомендации GitHub по вебхукам](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks).

В Cloudflare Queues одно сообщение ограничено 128 КБ: в очередь следует класть краткое подготовленное событие, а не безусловно весь исходный пакет GitHub. Сам GitHub ограничивает пакет вебхука 25 МБ, а список коммитов в `push` — 2 048 записями. Это дополнительные причины не строить уведомитель на предположении «в событии всегда есть абсолютно всё». [Ограничения Queues](https://developers.cloudflare.com/queues/platform/limits/), [состав событий GitHub](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push).

Для отправки карточки не требуется скачивать весь игровой репозиторий, подмодули, карты или изменения всех файлов. Достаточно данных события и, при необходимости, нескольких точечных запросов. Также не стоит одновременно публиковать «PR принят» и отдельную равнозначную карточку каждого коммита этого слияния. На первом этапе лучше выбрать ленту событий PR, а `push` включать отдельно для конкретной потребности.

Простой уведомитель не гарантирует отсутствие дублей после ручного повторного запуска или неоднозначного сетевого сбоя. Если требуется обновлять одну и ту же карточку PR и строго учитывать доставленные события, потребуется хранить соответствие событий и идентификаторов сообщений. Это аргумент в пользу посредника, а не обязательная часть первой версии.

## Как не сломать наследующие проекты

У Sunrise около 245 форков по счётчику GitHub, но это не число самостоятельных игровых проектов. Отдельно проверены активные публичные [fish-station](https://github.com/makura-games/fish-station), [lust-station](https://github.com/makura-games/lust-station) и [project-fire](https://github.com/makura-games/project-fire). У всех основная ветка `master`, есть сценарии публикации списков изменений, но GitHub возвращает `fork: false`. Поэтому проверка «это форк или нет» не решает вопрос подключения уведомлений.

Для варианта на Actions разумна общая реализация и небольшой вызывающий сценарий в каждом проекте. Правила, включение и секрет получателя задаются отдельно для каждого репозитория. Общий сценарий можно вызывать штатным механизмом повторного использования GitHub Actions. Передавать ему нужно только необходимый секрет, а не весь набор ключей публикации проекта. [Повторное использование сценариев](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows).

Подключение должно быть явным: например, отдельная переменная репозитория разрешает уведомления, а при её отсутствии они выключены ещё до выполнения работы. Скопированная конфигурация не должна автоматически подключать чужую копию к общему каналу. Название проекта берётся из текущего репозитория, без жёстко зашитого старого `space-sunrise`. Секреты и вебхуки не следует считать автоматически унаследованными вместе с файлами.

Для централизованного посредника можно настроить отдельные вебхуки репозиториев или один вебхук организации. Ещё вариант — **GitHub App, установленное приложение с выбранными репозиториями и правами**. Само по себе такое приложение не размещает обработчик: ему всё равно нужны Workers или свой сервер. Оно удобно для управляемого подключения разных владельцев, но не обязательно для первой версии. [Различия вебхуков GitHub](https://docs.github.com/en/webhooks/types-of-webhooks).

## Рекомендуемый порядок дальнейших действий

1. Выбрать минимальную ленту: открытия, готовность к рассмотрению, слияния и закрытия PR. Комментарии, редактирования и `push` сначала не переносить автоматически.
2. Если достаточно YAML и готового оформления — испытать Pipeline Pling в отдельном тестовом канале, добавив правила для служебных аккаунтов типа `User`. Если нужен самостоятельный TOML и своё оформление — сразу делать небольшой уведомитель Actions без промежуточной платформы.
3. Проверить человеческий PR из форка, оба исхода закрытия, действие бота над человеческим PR, длинное описание, большой набор коммитов, ответ `429` и повторный запуск. Это будущая проверка, не выполненные в рамках исследования тесты.
4. Подключить один наследующий проект с собственными правилами и получателем. Убедиться, что обычная копия репозитория ничего не отправляет без явного включения.
5. Только после проверки отключить заменённые категории в старой интеграции. Два действующих вебхука сначала сопоставить с каналами, чтобы не отключить нужную вторую ленту. Публикации обновлений для игроков оставить отдельно.

Если после фильтрации остаётся потребность пересылать сотни подробных событий, объединять сообщения за интервал и восстанавливать доставку после длительных сбоев, следующий шаг — общий посредник с очередью. Для нынешней задачи начинать с него необязательно.
